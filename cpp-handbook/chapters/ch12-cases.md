# Chapter 12: 案例索引（Cases）

## Core Idea
规则只有落到**可运行的代码**上才有用；案例真正的价值不在实现，而在**它旁边的单元测试**——
算法的边界条件写在测试里，不写在实现里。

## Frameworks Introduced
- **先写后看（Write Before Reading）**：独立写一版再看官方实现，比对差异。
  **When to use**：任何算法/题解类案例。**How**：先写 → 读实现 → 比对 → **读它的单测**。
- **读单测优先于读实现**：测试是边界条件的唯一权威来源。
  **When to use**：怀疑某个实现"看起来对"的时候。**How**：先看测试覆盖了哪些输入，再看实现怎么处理它们。
- **抄结构不抄实现**：拿走算法思路与数据结构选择，别拿走代码风格。
  **When to use**：把案例搬进自己的项目时。**How**：问自己"这个结构解决了什么问题"，而不是"这行代码怎么写的"。
- **可疑就查标准**：案例实现可能带过时写法。
  **When to use**：案例与你的编译器/标准版本不一致时。**How**：对照 `12-iso-draft/markdown/` 核实语义。

## Key Concepts
- **算法实现（Algorithm implementation）**：实现 + 示例 + 单元测试三件套，通常带 MIT 许可
- **LeetCode 题解（LC solution）**：按题号组织的 C++ 解法，一题一文件
- **工程示例（Engineering example）**：完整可编译的真实项目，看工程组织而非算法
- **教程配套代码（Tutorial code）**：每章的最小可运行示例
- **规范代码示例（Guideline examples）**：每条规则的**正例与反例**并列——最该逐条读的部分
- **题型索引（Problem-type index）**：按标签组织的问题清单，用来规划刷题顺序

## Mental Models
- **把案例当成"可执行的规格说明"**：它定义的是"什么输入会产生什么输出"，
  而不是"这段代码怎么写"。带着规格去看实现，比照着实现抄要有用得多。
- **测试是真相的边界**：实现可能偷懒，测试不会——没有测试覆盖的边界等于不存在。

## Anti-patterns
- **直接看答案**：等于没学。看过的东西不会变成你的能力，只变成"看起来熟悉"。
- **只读实现不读测试**：会漏掉所有边界条件，而边界条件正是你写不对的地方。
- **抄代码风格**：把别人的命名、缩进、错误处理一起搬进来，通常不适合你的项目。
- **相信案例里的过时写法**：案例可能用 C++98 风格实现 C++11 才有的问题。

## Worked Example
**用一次"二分查找"走完案例三步法。**

1. **先写（15 分钟）**：自己写出 `lower_bound`——边界条件用 `lo <= hi` 还是 `lo < hi`？
   空数组返回什么？`hi` 初值取 `n` 还是 `n-1`？这些你自己可能糊里糊涂。
2. **读实现**：打开 `07-algorithms/searching/` 里的实现。差异出现在边界写法上——
   你用的闭区间写法每次循环多一次判断；官方用左闭右开把 `n-1` 越界问题消掉了。
   **结构收获**：「用左闭右开统一表达区间」比记住某段代码更值钱。
3. **读单测（关键一步）**：看测试里有哪些输入——空数组、单元素、元素不存在、重复元素、
   全大于/全小于。把你写的版本拿这些输入跑一遍，
   **大概率在"元素不存在"这一条上行为不一致**（返回 `end()` 还是 `n`？）。
   这个差异就是"边界条件在测试里"的实证。

三步走完，你记住的不是那段代码，而是「二分查找的边界语义」和「我的实现在空/缺失输入上的行为」。

## Key Takeaways
1. 先写后看，直接看答案等于没学。
2. 读单测——边界条件在测试里，不在实现里。
3. 抄结构不抄实现：拿走思路，不拿走风格。
4. 案例里的实现可能过时；语义存疑就查标准草案。
5. 规范类案例（正例 + 反例并列）是最该逐条读的部分，因为反例直接对应真实的 bug 形态。
6. 题型索引用来规划顺序，不要按题号从 1 刷到 4000。
