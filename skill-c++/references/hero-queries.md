# 触发路由评测集（hero queries）

本文件评测的是**另一个层面**的问题：`references/routing-eval.jsonl` 测的是「已经加载本 skill 之后，
该读哪一章」；本文件测的是「这条提问该不该加载本 skill」。

判据来自 `SKILL.md` front-matter 的 `description`：写 C++ 代码、做 C++ 代码评审、排查崩溃/数据竞争/
内存错误、查 C++ Core Guidelines 规则原文时使用。评测时人工或模型逐条判定「命中 / 不命中」，
正负两类都要过——只会认正例的路由等于没有路由。

## 一、正向（10 条）：应该命中本 skill

| # | 提问 | 期望结果 | 判定依据 |
|---|---|---|---|
| P01 | 帮我 review 这段 C++ 代码 | 命中 | 典型 C++ 代码评审请求，直接落在 description 的「做 C++ 代码评审」上 |
| P02 | 这段代码有没有数据竞争？ | 命中 | 并发缺陷排查，属 description 的「排查崩溃/数据竞争」，ch05 覆盖 |
| P03 | ASan 报的 heap-use-after-free 怎么查？ | 命中 | Sanitizer 报告排查，description 的「内存错误」+ ch10 的工具链 |
| P04 | shared_ptr 循环引用怎么破？ | 命中 | C++ 所有权核心问题，ch01 覆盖 |
| P05 | std::move 和 std::forward 到底怎么用？ | 命中 | C++ 移动语义 API 用法，ch02 覆盖 |
| P06 | 模板报错一堆，SFINAE 和 Concepts 怎么选？ | 命中 | C++ 模板与 Concepts，ch03 覆盖 |
| P07 | vector 扩容导致迭代器失效，erase-remove 写法对吗？ | 命中 | STL 容器与算法选型，ch04 覆盖 |
| P08 | C++20 有哪些特性是真值得用的？ | 命中 | C++20 特性选型，ch08 覆盖 |
| P09 | CMake 工程实践怎么搭，警告即错误和单元测试怎么接？ | 命中 | C++ 工程实践，ch09 覆盖 |
| P10 | 这段 C++ 有虚析构和整数溢出的坑吗？ | 命中 | C++ 陷阱与反模式，ch11 覆盖 |

|---|---|---|---|
| N01 | 帮我写个 Python 脚本读 CSV | 不命中 | 纯 Python 脚本任务，与 C++ 知识无关，应交给 Python/通用编码 skill |

## 三、邻接混淆（4 条）：两边都沾边，但本 skill 更合适

| # | 提问 | 期望结果 | 判定依据 |
|---|---|---|---|
| A01 | Rust 的所有权和 C++ 的智能指针有什么区别？ | 命中本 skill | 问题主体是 C++ 所有权模型的语义对照，Rust 只是参照系；ch01 的单一主人/RAII/Rule of Zero 正好是答案骨架 |
| A02 | 帮我写一段 Java 的线程安全代码 | 命中本 skill（并发心智模型） | 「线程安全」的可迁移知识在 ch05：先证明无数据竞争、锁与数据放一起定义、内存序选型；Java 的 API 细节交给别的 skill |
| A03 | C++ 的模板和 Rust 的泛型哪个更强？ | 命中本 skill | 对照的锚点是 C++ 模板/Concepts 约束写法（ch03），本 skill 提供 C++ 一侧的可执行判据 |
| A04 | Go 的 goroutine 和 C++ 的线程池该怎么设计？ | 命中本 skill | 对照的锚点是 C++ 线程池与并发模型（ch05），并发的「先证明再优化」口径来自本 skill |

## 使用说明

- 正向 10 条必须全中、负向 5 条必须全不中——负例用来抓「凡是有技术词就加载」的过度触发。
- 邻接 4 条的期望是「本 skill 更合适」，但要接受「模型同时加载邻近 skill」的答案：只要本 skill
  被加载即算通过，因为 C++ 一侧的判据只能从这里拿。
- 这套题与 `references/routing-eval.jsonl` 是两级评测：前者管**要不要加载**，后者管**加载后读哪章**。
  配套脚本：`python scripts\route_eval.py`（章节路由回归）。
